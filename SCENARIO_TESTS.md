## Прогон 2026-08-20 — Часть D (Deploy Verification / Idempotency / Security-SSRF / Regression grep)

**D1 (Deploy Verification):** не применялось — код приложения не менялся (только тесты), деплой не требуется.

**D2 (Idempotency):** добавлены 2 теста. `delete_media_package` уже проверяет существование пакета перед удалением — второй вызов подряд получает чистую ошибку not-found. `delete_asset_image` подтверждён естественно идемпотентным — после первого удаления путь/url уже пустые, повторный вызов на том же role+version не находит что чистить ещё раз, но остаётся успешным, не падает.

**D3 (Security/SSRF) — нетривиальный случай, разобран отдельно:** в `magnific_client.py` есть настоящий `download_image_bytes`, который делает `httpx.AsyncClient().get(url)` на произвольный URL БЕЗ allowlist (осознанное архитектурное решение — задокументировано в самом коде: `ctx.http` портит бинарные байты через свой text-decode, поэтому здесь намеренно используется сырой httpx). Это реальная SSRF-поверхность по форме вызова. Но она безопасна по построению: каждый вызов `download_image_bytes` во всех местах `handlers.py` получает URL, который сам пришёл из ответа Magnific/Freepik API (результат генерации, апскейла, Mystic-задачи) — никогда напрямую из пользовательского ввода в чате. Добавлен 1 regression-тест: grep по исходнику `handlers.py`, который падает, если когда-либо появится вызов `download_image_bytes(params....)` — то есть URL, пришедший прямо из параметров запроса, а не из ответа провайдера.

**D4 (Regression grep):** нет новых находок специфичных для этого приложения сверх `Docs/known-bug-patterns.md`.

**Итог:** 316/316 тестов зелёные (было 311). Реальных багов не найдено; SSRF-поверхность идентифицирована, разобрана и подтверждена безопасной по конструкции.

## Прогон 2026-08-19

**Существующее покрытие до PST:** 308 тестов в 22 файлах — самое глубокое
покрытие среди всех приложений, пройденных в этом сквозном прогоне
(генерация, upscaling, prompt engine, model discovery, panels, pricing,
recovery-логика сопоставления). Аудит по точному имени `@chat.function`
нашёл **ровно одну** функцию, никогда не вызывавшуюся на уровне хендлера:
`recover_stored_images`. Её внутренние хелперы в `recovery.py`
(`match_creation_urls`, `list_recent_creations`) уже тестировались
напрямую в `test_recovery.py` — но сам handler (полный поток: чтение
пакетов, скачивание байт, запись в постоянное хранилище, апдейт пакета)
не был покрыт.

**Новый файл:** `tests/test_pst_scenarios.py` — 5 сценариев: blocked (нет
Magnific API key), happy no-op (нечего восстанавливать — валидный успех,
не ошибка), happy full recovery (легаси-ассет без `original_storage_path`
восстанавливается, `restored` счётчик растёт, пакет обновляется), error
(скачивание с провайдера падает — актив помечается `unavailable`, не
падает исключением), adversarial (пакет уже с `original_storage_path` —
идемпотентность: recovery не трогает уже сохранённые активы).

### Результат

313/313 тестов зелёные (308 существующих + 5 новых). **Реальных багов в
приложении не найдено.**
